 Целевая архитектура: федерация по семействам документов


## 0. Правило пересмотра правил

Все правила проекта — принципы, решения, договорённости этого документа и любые будущие — пересматриваются с согласия пользователя. 
Правило существует, чтобы помогать развитию, а не мешать ему: если правило мешает развитию, или мы понимаем, что оно было ошибочным, 
или оно стало ошибочным из‑за новых обстоятельств, мы его пересматриваем. 
Ни одно правило не считается «неприкасаемым»

Зачем
Главный выигрыш федерации — организационный, а не вычислительный: 
семейства документов наполняются независимо разными людьми или агентами, не мешая друг другу, и выкатываются независимо.

## Принципы

1. **У документа ровно один дом — сервер семейства.** Семейство определяется издателем (с предшественниками) 
и грубым классом формы документа. 
На практике семейство равно «одна площадка публикации, один конвейер наполнения, одна схема адресов, один характер обязательности». 
Документ попадает в семейство по детерминированной таблице правил от пары «издатель, тип»; таблица версионируется.
2. **Область (`domain`) — многозначный тег, а не партиция.** 
Один закон регулирует несколько областей, поэтому делить серверы по областям нельзя: документы дублировались бы. 
Область хранится внутри сервера семейства (на документе или на разделе) и работает как фильтр поиска.
3. **Блок — продуктовая упаковка.** 
Таблица в конфигурации агрегатора раскладывает блок в набор семейств и фильтр областей. «Санитария» = санитарные правила + законы (фильтр по области) + акты Правительства (фильтр) + стандарты с методиками (фильтр). 
4. **Один код, N развёртываний.** Все серверы семейств — один образ и один пакет, различаются конфигурацией и данными. 
Миграции, тесты, чек‑листы остаются одними. 
Это модульный монолит, развёрнутый по семействам, а не микросервисы с разными кодовыми базами.
5. **Агрегатор тонкий.** Вход (ключи, квоты, журнал), маршрутизация, разветвление, сборка. 
Каталог документов и реранкер — отдельные сервисы. 
Агрегатор без состояния, кроме конфигурации, и масштабируется копиями.
7. **Качество измеряется на трёх уровнях:** эталон семейства, эталон маршрутизации (вопрос → ожидаемые семейства), сквозной эталон через агрегатор. 
Изменение маршрутизатора или сшивки без прогона не выкатывается.
8. **Запросы клиентов обрабатываются в России** — правило распространяется на маршрутизатор и общий реранкер агрегатора.

## 3. Семейства документов

Список семейств задаётся явно и растёт по мере подключения источников. 
Издатели указаны с предшественниками, потому что дом документа не меняется от переименования ведомства.

| Семейство | Издатели (с предшественниками) | Формы | Источник |
|---|---|---|---|
| санитарные правила | Главный государственный санитарный врач, Роспотребнадзор, ранее Минздрав и Госкомсанэпиднадзор | СанПиН, санитарные СП, СН, ГН, МУ, МР | publication.pravo.gov.ru, rospotrebnadzor.ru |
| федеральные законы | Государственная Дума | ФЗ, кодексы | ИПС pravo.gov.ru |
| акты Правительства | Правительство РФ | постановления, распоряжения | publication.pravo.gov.ru |
| указы | Президент РФ | указы | publication.pravo.gov.ru |
| строительные нормы | Минстрой, ранее Госстрой | строительные СП, СНиП | minstroyrf.gov.ru, ФГИС ЦС |
| стандарты | Росстандарт, Межгосударственный совет по стандартизации | ГОСТ, ГОСТ Р, ПНСТ | ФГИС Росстандарта |
| пожарная безопасность | МЧС | правила противопожарного режима, пожарные СП, НПБ | mchs.gov.ru, publication.pravo.gov.ru |
| охрана труда | Минтруд | приказы с правилами по охране труда | publication.pravo.gov.ru |
| акты Банка России | Банк России | положения, инструкции, указания | cbr.ru |
| техрегламенты ЕАЭС | ЕЭК, ранее Комиссия Таможенного союза | ТР ТС, решения | eurasiancommission.org |

Почему не проще:

- **Только издатель** ломается на преемниках (СанПиНы выпускали три ведомства) и на разношёрстности (Росстандарт и МГС дают ГОСТ с одной структурой).
- **Только тип** ломается на родовых формах: «приказ» есть у каждого министерства, «постановление» — у Правительства и Главсанврача, «СП» — и санитарные, и строительные с разной структурой и площадками.
- **Издатель плюс тип буквально** даёт взрыв мелких серверов и разветвление в пять серверов там, где достаточно двух.

Типы документов остаются внешним словарём для клиентов; агрегатор переводит 
тип в семейства: ГОСТ → стандарты, ФЗ → законы, СП → санитарные правила и строительные нормы (дальше решает фильтр области). 
Схема адресов становится свойством семейства.

к примеру Типичное разветвление санитарного вопроса — три семейства: санитарные правила, законы, акты Правительства. 
Это норма, а не исключение, поэтому сшивка через общий реранкер нужна с первого же второго сервера.

- **Сервер внутренний:** доверяет агрегатору, своих клиентских ключей не имеет.

## 5. Агрегатор

Для клиента — обычный MCP‑сервер с теми же инструментами. Для семейств — клиент по HTTP. Четыре части:

- **Вход.** Ключ организации → оплаченные блоки, квота, запись в журнал запросов. Тонкая прослойка без бизнес‑логики.
- **Маршрутизатор.** Три источника решения по приоритету: явная область, блок или типы от клиента; идентификатор документа для адресных инструментов (детерминированно, через каталог); классификатор для свободного текста — только когда первых двух нет. Классификатор без LLM в основном пути: эмбеддинг запроса против примеров запросов на семейство (как в библиотеке semantic‑router), миллисекунды; при малом разрыве между кандидатами — в несколько семейств; лёгкая модель — только для спорных случаев. 
Решение кэшируется и записывается в журнал — из журнала строится эталон маршрутизации.
- **Разветвление.** Параллельные вызовы с таймаутом на семейство. Не ответившее семейство не роняет ответ, а попадает в `degraded` с именем семейства.
- **Сборка.** Оценки разных серверов несравнимы, складывать их нельзя. Основной путь: объединить верхушки от всех семейств и прогнать через общий реранкер. 
Деградация при недоступном реранкере: чередование по доле уверенности маршрутизатора с пометкой в `degraded`. 
Чередование не является нормальным режимом: опрос нерелевантных источников и их наивное слияние ухудшают ответ (FeB4RAG).

Единица тарифа — вызов клиента, сколько бы семейств под ним ни отработало. Внутренние вызовы считаются отдельно для себестоимости.

Каталог документов (документ → семейство, статус, синонимы, замены) и реранкер живут отдельно. 
Через каталог разрешаются перекрёстные ссылки между семействами (СанПиН → ГОСТ с методикой) и обслуживаются `list_documents` и `get_document_info`.

## некоторые наброски 


Локальное правило семейства: git для малых семейств, для больших — хранилище по решению семейства; индекс по‑прежнему производная |
Локальное правило семейства со своей площадкой |
Схема адресов — свойство семейства; общей остаётся форма `doc_id` с семейством внутри или отображение через каталог |
Размерность, смена модели Локально для семейства; агрегатор сливает тексты через реранкер, не векторы |
Организации, ключи, журнал  Переезжают в агрегатор; серверы семейств внутренние |

## 8. Что федерация не решает

- **Масштаб внутри семейства.** Семейство стандартов само по себе огромно; внутри него нужны метаданные по объектам и классификаторам, иерархический поиск 
(сначала документы, потом чанки), свой рубрикатор. Это самый дорогой по подготовке данных блок.
- **Тегирование областей** — ручная или агентская работа на каждый документ; для законов и стандартов дороже парсинга. Без неё не работает ни одна схема сужения.
- **Вопросы на стыке областей** требуют поиска в нескольких семействах и сшивания; редки, решаются на уровне агента.
- **Общие термины без контекста** («температура», «срок хранения») остаются плохими запросами при любой архитектуре; лечится уточнением области агентом.



Альтернатива без сшивки — шлюз отдаёт клиенту по одному инструменту поиска на семейство, а маршрутизирует модель клиента. Возможна как режим для продвинутых клиентов, основным не делается: качество маршрутизации тогда не наше, а плохой выбор источников портит ответ.
