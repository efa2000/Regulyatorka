# Архитектура: федерация по семействам документов

Семейства наполняются независимо разными людьми или агентами и выкатываются независимо. Выигрыш организационный, не вычислительный.

## Принципы

1. **У документа один дом — сервер семейства.** Семейство = издатель (с предшественниками) + грубый класс формы документа. На практике: одна площадка публикации, один конвейер наполнения, одна схема адресов, один характер обязательности. Документ попадает в семейство по детерминированной версионируемой таблице «издатель, тип → семейство».
2. **Область (`domain`) — многозначный тег, не партиция.** Один закон регулирует несколько областей, делить серверы по областям нельзя. Хранится внутри семейства на документе или разделе, работает как фильтр поиска.
3. **Блок — продуктовая упаковка.** Конфигурация агрегатора раскладывает блок в набор семейств и фильтр областей. «Санитария» = санитарные правила + законы (фильтр по области) + акты Правительства (фильтр) + стандарты с методиками (фильтр).
4. **Один код, N развёртываний.** Все серверы семейств — один образ, различаются конфигурацией и данными. Модульный монолит, не микросервисы.
5. **Агрегатор тонкий.** Вход, маршрутизация, разветвление, сборка. Без состояния, кроме конфигурации; масштабируется копиями. Каталог документов и реранкер — отдельные сервисы.
6. **Качество на трёх уровнях.** Эталон семейства, эталон маршрутизации (вопрос → ожидаемые семейства), сквозной эталон через агрегатор. Маршрутизатор и сшивка без прогона не выкатываются.
7. **Запросы клиентов обрабатываются в России** — включая маршрутизатор и реранкер агрегатора.

## Семейства

Список явный, растёт по мере подключения источников. Издатели с предшественниками: дом документа не меняется от переименования ведомства.

| Семейство | Издатели | Формы | Источник |
|---|---|---|---|
| санитарные правила | Главный государственный санитарный врач, Роспотребнадзор, ранее Минздрав и Госкомсанэпиднадзор | СанПиН, санитарные СП, СН, ГН, МУ, МР | publication.pravo.gov.ru, rospotrebnadzor.ru |
| федеральные законы | Государственная Дума | ФЗ, кодексы | ИПС pravo.gov.ru |
| акты Правительства | Правительство РФ | постановления, распоряжения | publication.pravo.gov.ru |
| указы | Президент РФ | указы | publication.pravo.gov.ru |
| строительные нормы | Минстрой, ранее Госстрой | строительные СП, СНиП | minstroyrf.gov.ru, ФГИС ЦС |
| стандарты | Росстандарт, Межгосударственный совет по стандартизации | ГОСТ, ГОСТ Р, ПНСТ | ФГИС Росстандарта |
| пожарная безопасность | МЧС | правила противопожарного режима, пожарные СП, НПБ | mchs.gov.ru, publication.pravo.gov.ru |
| охрана труда | Минтруд | приказы с правилами по охране труда | publication.pravo.gov.ru |
| акты Банка России | Банк России | положения, инструкции, указания | cbr.ru |
| техрегламенты ЕАЭС | ЕЭК, ранее Комиссия Таможенного союза | ТР ТС, решения | eurasiancommission.org |

Почему издатель + класс формы, а не проще:
- только издатель ломается на преемниках (СанПиНы выпускали три ведомства) и на разных издателях с одной структурой (ГОСТ у Росстандарта и МГС);
- только тип ломается на родовых формах: «приказ» есть у каждого министерства, «СП» — и санитарные, и строительные с разной структурой;
- издатель + тип буквально даёт взрыв мелких серверов.

Типы документов — внешний словарь для клиентов; агрегатор переводит тип в семейства: ГОСТ → стандарты, ФЗ → законы, СП → санитарные правила и строительные нормы, дальше решает фильтр области. Схема адресов — свойство семейства.

Типичный санитарный вопрос уходит в три семейства (санитарные правила, законы, акты Правительства). Это норма, поэтому сшивка через общий реранкер нужна со второго же сервера.

## Сервер семейства

- **Внутренний.** Доверяет агрегатору, своих клиентских ключей не имеет.
- **Методы.** Поиск, `get_clause`, возможности (семейство, типы документов, наличие таблицы нормативов, `base_version` — версия базы), здоровье.
- **Элемент результата.** `chunk_id`, `doc_id`, `address`, `url`, текст, статус, `score`, `base_version`. `chunk_id` — непрозрачный ключ: агрегатор его структуру не знает и передаёт обратно в `get_clause` нужному серверу. `address` — строка для человека и цитаты; разбор адреса на части (раздел, пункт, таблица) остаётся внутри семейства. `score` — локальная оценка семейства, между семействами не сравнивается.
- **`url`** — ссылка для человека: открывает документ как Markdown на простой странице и показывает его в нужном месте (раздел, пункт). Не скан и не PDF; официальное опубликование остаётся в `source_url`.
- **Локально для семейства.** Хранилище текстов (git для малых, иное для больших; индекс — производная), политика источников, парсер и чанкинг, схема адресов, модель эмбеддингов и размерность, таблица нормативов, эталон вопросов, мониторинг источника, воркеры наполнения (скрипты, агенты, люди).

Пример элемента результата:

```json
{
  "chunk_id": "sp-2.4.3648-20:2.4.6",
  "doc_id": "sp-2.4.3648-20",
  "doc_short": "СП 2.4.3648-20",
  "doc_title": "Санитарно-эпидемиологические требования к организациям воспитания и обучения…",
  "doc_status": "active",
  "address": "СП 2.4.3648-20, п. 2.4.6",
  "url": "https://mcp.regulyatorka.ru/doc/sp-2.4.3648-20/2.4.6",
  "kind": "clause",
  "text": "2.4.6. Учебные помещения …",
  "score": 0.91,
  "source_url": "http://publication.pravo.gov.ru/Document/View/0001202012210122",
  "edition_date": "2025-09-01",

}
```

## Агрегатор

Для клиента — обычный MCP-сервер с теми же инструментами. Для семейств — HTTP-клиент.

- **Вход.** Ключ организации → оплаченные блоки, квота, журнал запросов. Без бизнес-логики.
- **Маршрутизатор.** По приоритету: явная область, блок или типы от клиента; идентификатор документа для адресных инструментов — детерминированно через каталог; классификатор свободного текста — только когда первых двух нет. Классификатор без LLM: эмбеддинг запроса против примеров запросов на семейство (как в semantic-router), миллисекунды; при малом разрыве — в несколько семейств; лёгкая модель — только для спорных случаев. Решение кэшируется и пишется в журнал; из журнала строится эталон маршрутизации.
- **Разветвление.** Параллельно, таймаут на семейство. Не ответившее семейство не роняет ответ, а попадает в `degraded` с именем.
- **Сборка.** Оценки разных серверов несравнимы, складывать нельзя. Основной путь: объединить верхушки от всех семейств и прогнать через общий реранкер. Реранкер недоступен — чередование по уверенности маршрутизатора с пометкой в `degraded`. Это аварийный режим: наивное слияние нерелевантных источников ухудшает ответ (FeB4RAG).
- **Тариф.** Единица — вызов клиента, сколько бы семейств ни отработало. Внутренние вызовы считаем отдельно для себестоимости.

## Каталог документов

Документ → семейство, статус, синонимы, замены. Обслуживает `list_documents`, `get_document_info`, перекрёстные ссылки между семействами (СанПиН → ГОСТ с методикой) и детерминированную маршрутизацию по идентификатору.

## Чего федерация не решает

- **Масштаб внутри семейства стандартов.** Нужны метаданные по объектам и классификаторам, иерархический поиск (сначала документы, потом чанки), свой рубрикатор. Самый дорогой блок по подготовке данных.
- **Тегирование областей.** Ручная или агентская работа на каждый документ; для законов и стандартов дороже парсинга. Без него не работает ни одна схема сужения.
- **Вопросы на стыке областей.** Несколько семейств и сшивка; редки, решаются агентом.
- **Общие термины без контекста** («температура», «срок хранения») — плохие запросы при любой архитектуре; лечится уточнением области агентом.

Альтернатива без сшивки — по инструменту поиска на семейство, маршрутизирует модель клиента. Возможна как режим для продвинутых клиентов, основным не делается: качество маршрутизации тогда не наше.
